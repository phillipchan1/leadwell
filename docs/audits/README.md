# Audits

Point-in-time reviews of the app against the docs. One file per audit:
`YYYY-MM-DD-<scope>.md`, from
[`../templates/audit.md`](../templates/audit.md).

**Never edit a past audit.** They're a record of what was true then; the trend
across them is the actual value.

## When to run one

- After any significant release
- Quarterly, regardless
- When something feels off but you can't name it — the audit's job is to name it
- Before deciding a roadmap, so the decision is grounded in the real gap

## Two-way street

An audit can find that the **doc** is wrong, not the app. Both outcomes are
valid findings. The last section of every audit is doc corrections for exactly
this reason — an audit that only ever criticizes the code is being run wrong.

## The sharpest single measure

Section 2 of the template: for each leadership mode, count how many of the
questions in
[`../product/leadership-modes.md`](../product/leadership-modes.md) the app can
actually help answer. It's a blunt number that's hard to fool yourself about,
and tracking it across audits shows whether the product is getting deeper or
just wider.

## Baseline

The gap analysis in
[`../product/surface-map.md`](../product/surface-map.md) is the informal
baseline as of 2026-07. The first real audit should confirm or correct it.
